# 手动价值流程→产品 (Manual Valuable Process → Product)

## R — 原文 (Reading)

> "我决定真正从头开始时,把创业等同于雇佣他人或写代码的事都先放一边。我只是去想办法解决一个具体的人的具体问题。我从最小的那步开始:亲自做。手动交付。如果客户付钱了,就再给下一个客户做同样一件事。做到第三、第四个客户时,我把每一步记录下来——这就是 processize(流程化)。在第八、第十二个客户那里,我开始看出哪些步骤会反复出现、哪些可以被自动化——这才该写代码。"
>
> — Sahil Lavingia, Chapter 3 "Build as Little as Possible",《The Minimalist Entrepreneur》

---

## I — 方法论骨架 (Interpretation)

这条原则主张:在你和"有人愿为你没写出来的解决方案付钱"之间,只有一条最短路径——你自己手动做。不要先去搞 App、搞 SaaS、搞自动化、搞网站。建立一个能交付价值的流程——可能 100% 由你手动、邮件、电话、Google Sheet 完成——这就是真正的 MVP(Manual Valuable Process,可售卖的手动过程)。这条路径在产品代码之前,做这件事的副产品有三:

1. **付费信号零噪音**:人们愿为"未经包装的真实流程"付钱,说明需求真;不愿,说明你回避了一个早该回避的失败。
2. **流程手册(SOP)**:每做一个客户你都写下"我刚才具体做了什么",积累出来的就是未来产品化的蓝图。
3. **客户关系与口碑**:手动前 10 个客户的过程同时是你和他们建立信任的过程,口碑来源。

跑通手动流程之后才考虑 productize(自动化)。判据朴素得像一句谚语:**"手动都卖不出去,自动化也没用。"**

## A1 — 书中的应用 (Past Application)

### 案例 1: Derek Sivers / CD Baby — 手动先于自动化 (c06)

- **问题**: Sivers 想帮独立音乐人把 CD 放到网上卖。
- **方法论的使用**: 头几周他不写一行代码。客户打电话来,他记下订单、自己跑去唱片店进货、亲手包装、开车去邮局寄——全部人工完成。把每一次"接订单→收钱→拿货→发货"画成流程,前后做了几十个客户才算"有了 playbook"。
- **结论**: 只有当手动流程跑通、订单量超过他一个人能处理的阈值,才开始写网站、做支付、做后台。
- **结果**: CD Baby 成为独立音乐发行先驱,Sivers 创立时未融一分钱、纯人手起家,最终 $2200 万卖给 Disc Makers。

### 案例 2: Anna Gőt / Interintellect — 沙龙先于 App (c05)

- **问题**: Anna 看到一群知识工作者想找高质量的深度讨论空间,但所有人都在建 App / 在线论坛。
- **方法论的使用**: 别人都做线上的事,她反而去组织线下+邮件沙龙。每次现场活动她手动写主持提纲、跑签到、跟进会后邮件,4 周时间打磨出 4 个"必谈问题"的方法论。没有任何 App/网站,沙龙反而成了产品本体的说明书。
- **结论**: 等到沙龙能稳定每晚运行 60+ 场/日,她才把主持人手册做成可下载模板——这本身就是"产品化"的第一级。
- **结果**: Interintellect 成为学术讨论沙龙的头部品牌,业务能持续、可持续盈利,反例是同一个市场里大量先烧钱做 App 的同类项目已销声匿迹。

### 案例 3: Lynda Weinman / Lynda.com — 书本与课程先于订阅视频 (c07)

- **问题**: Lynda 教网页设计,先后出过书、教过线下课。
- **方法论的使用**: 长期手动交付教学价值(写书、办讲座、当面辅导),积累了完整的教学流程和受众订阅意愿。她没有立刻去"做个视频订阅平台",而是先把现有受众、课程内容、教学反馈几十年积累完毕,再决定产品形态。
- **结论**: 当订阅视频业务上线时,她已知:她教的什么、目标受众是谁、他们为何会月费买,痛点早已被她"手动教过"千百遍验证过。
- **结果**: Lynda.com 被 LinkedIn 以 $15 亿美元收购,是订阅模式复利力量的经典案例。

### 案例 4: Justin Mitchell / Yac — 黑客松 4 天做出真问题 (c08)

- **问题**: Justin 在远程团队里被异步语音消息折磨(纯文本说不清、开会太重)。
- **方法论的使用**: Product Hunt 黑客松 4 天里,他没做完整产品。MVP 是"一个表单+一个 Slack bot":同事提交语音消息,bot 直接转写到 Slack。功能极简陋,但已能让 5 个真实团队用起来。
- **结论**: 手动连通了"录→传→听→反馈"这条链,验证了"异步语音消息"真有需求,然后才演进为完整产品 Yac。
- **结果**: Yac 成为远程团队异步沟通领域的早期先驱,验证了"黑客松就是手动 MVP"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 创业者已经做了 5-10 个客户访谈、听到了反复出现的具体抱怨,准备动手做东西时——比"我想做个 App"更接近下游。
2. 自由职业者已经在手动服务一些客户,考虑要不要"做套 SaaS 让客户自助"时。
3. 创业者已经在手动帮朋友/同事解决某类问题,想把"做好事"变成可持续业务时。
4. 创业者要做一个内部职能(运营、客服、招聘、内容生产),已经在考虑"该写脚本/流程化"时。

### 语言信号 (用户的话里出现这些就应激活)

- "我想做个 MVP / 最小版本 / Demo / 试试水。"
- "我们要不要外包做个 App? / 我们要不要招个工程师?"
- "先做个小程序跑通?"
- "做个产品 / 写个脚本 / 建个系统?"
- "能不能先做一个能用的版本看看?"

### 与相邻 skill 的区分

- **vs `right-size-business-sequencing` (序列纪律)**: 本 skill 是序列中的第 3 步 (Build as Little as Possible) 的执行细节
- **vs `community-first-niche-selection` (社区优先)**: 本 skill 通常依赖前一步 — 你已经知道在哪群人了,才能决定用手工方式给他们交付什么
- **vs `founder-led-sales-process` (创始人亲售)**: 都是 manual-first 阶段, 但本 skill 是"怎么交付价值"; 那个 skill 是"怎么把它换成钱"

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **停 + 问"那能不写代码先动手吗?"**
   - 完成标准: 用户能在 30 秒内说出"我要先做哪件手动的事、为谁做、收到什么样证据算他/她满意"。
   - 判停: 若用户说"我不关心有没有人付钱、只想做出来看看",立即停在本步骤并提示此场景不适用。

2. **画一张《一客户流》表 (One-Customer Flow)**
   - 完成标准: 一张表格列出从客户找你 → 你交付 → 客户付钱 → 你跟进 这条链上所有具体动作(越细越好,精确到用了什么工具、说了什么话)。该表每个条目都应是可手写、可打电话、可发邮件完成,不允许出现"自动化""集成""触发器"。

3. **找 3-10 个真实客户用手动流程服务一遍**
   - 完成标准:
     a. 至少 3 个**真实付费**客户(哪怕只收 1 美元);
     b. 每个客户的服务全过程被记录到《一客户流》;
     c. 每个客户付款后你至少问过他一次"你愿不愿为这事付更多 / 推荐朋友来"。
   - 判停: 若 3 人都拒付(或连 1 美元都不愿付),回到 s02 重新检验痛点;不要绕过去写代码。

4. **Processize: 抽取每客户共性动作成 SOP**
   - 完成标准: 一份 1-2 页的 SOP 清单,任何按它做的人(家人/朋友/自由职业者)都能在不读你脑子的情况下交付等价价值。

5. **决定是否 Productize — 并设置触发条件**
   - 完成标准: 仅当 (a) 手动流程的瓶颈已**痛到你再做一个就要少睡觉**,且 (b) 你已能稳定赚到钱、且 (c) SOP 足够稳定时,才进入 Productize。在那之前所有"提高自动化"的工作都是浪费。
   - 判停: 若仅满足上述条件之一,继续手动;不要被"竞争对手在自动化"吓到而提前 productize。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **已有付费用户、瓶颈是规模**: 直接 productize,本 skill 不该被用作延迟自动化借口。
- **纯个人工具 / 无外部客户**: 你自己就是唯一用户,不存在"付费信号",不需要手动流程阶段,直接做产品甚至不需做都行。
- **需要严格合规的事**(医疗诊断、税务建议、法律意见): 手动阶段中可能触线,应在合规框架下并行设计产品形态,而非纯手动试跑。
- **客户对象是组织而非个人**: 手动流程对一个 B2B 决策链可能无效——不是不该手动,而是手动阶段就要做到对接采购流程,不是盲目跑通。

### 作者在书中警告的失败模式

- **ce07 — 先写代码再做客户访谈**: 用户工作时间中"和客户聊"占比低于 20% 时,本 skill 的触发前提已经失败。
- **ce08 — 死磕技术方案而忽视已浮现的非技术方案**: 听到客户说"我手动 X 也行"你不爽——这正是本 skill 的核心信号,不是该生气的部分。
- **ce11 — 等产品"完美"才上线**: 反向使用本 skill——拖到"完美"恰恰是手动能办到的、自动化却办不到的反面。
- **ce14 — 跳过"动手能力"环节,直接外包或自动化**: 高效率幻觉;雇了客服/运营但你自己没服务过一个客户时,应立刻关掉自动化思考,回到本 skill。
- **ce22 — 雇人 / 扩张时跳过"痛到不得不雇"的临界点**: 本 skill 第 5 步直接给出判断"痛到不招不行"才算数。

### 作者的盲点 / 时代局限

- 本原则在"软件产品"以外的领域更难直接套用:实体产品(硬件、餐饮)客户一多就有库存与物料成本,纯手动阶段可能现金流先垮,需配套小批量按需生产(minimal batching)而非"先全手工"。
- 作者未明确"多长算足够"。书中 Anna Gőt 给 4 周,Derek Sivers 给几周。本 skill 给出的是 3-10 个付费客户的客观阈值而非时间长度,尽量不绑时间。

### 容易混淆的邻近方法论

- **MVP (Minimum Viable Product,硅谷版)** : 这里的最小仍是"产品的最简版本";本 skill 把 MVP 重定义为 Manual Valuable Process,优先级更高。
- **Design Sprint / Prototype**: 一次性时间盒式设计冲刺,产出 throwaway prototype;本 skill 是可重复的服务流程,产出真付费客户且没有"丢"的设计。
- **Concierge MVP**: 一种具体形态——你像专属管家一样服务一个客户。本 skill 是 Concierge 的扩展,覆盖手册化、自动化与不自动化决策。
